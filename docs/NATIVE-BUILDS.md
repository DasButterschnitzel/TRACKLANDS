# Native builds (Windows, Android)

The native apps are the same game as the web version, wrapped in a
[Tauri 2](https://v2.tauri.app/) shell. Simulation, Three.js, saves and all
assets are the unchanged web code. `src-tauri/` holds a small Rust host that
opens it in the operating system's WebView:

- **Windows:** WebView2
- **Android:** Android System WebView
- **Linux** (development only): WebKitGTK

Normal releases are built by GitHub Actions; see
[RELEASING.md](RELEASING.md). This page is for building locally and
understanding the pieces.

## How the pieces fit

```
index.html, src/, styles/, vendor/three/, icons/, assets/   ← the game (no build step)
        │  tools/runtime-files.mjs   one list of runtime files
        ├─▶ service-worker.js        (web: offline cache)        tools/build-sw.mjs
        ├─▶ dist/web/  + web zip     (web release)               tools/build-web.mjs --target=web --zip
        └─▶ dist/native/             (Tauri frontendDist)        tools/build-web.mjs --target=native
                 │
                 └─▶ src-tauri/  → Windows NSIS installer, Android APK/AAB
```

- **Staging.** `dist/native` contains only runtime files, without a service
  worker. The staging step checks that every module, stylesheet, page and
  music playlist reference resolves inside the staged tree. It also checks
  that no development folder is shipped (tests, trailer, docs, tools,
  src-tauri).
- **Music.** Files in `assets/music/` ship automatically in every build. Add
  the files and their entries in `assets/music/music.json`; nothing else
  needs to change.
- **Service worker.** The native app never registers it (`src/platform.js`),
  because it ships every file already and must not run a stale cached copy of
  itself. The browser and PWA keep the service worker unchanged.
- **Native differences** are all in `src/platform.js`:
  - save export, diagnostics and photos use the system "save as" dialog
    (Tauri dialog and fs plugins);
  - the Android Back button closes the top layer, in the same order as
    Escape: driver mode, construction drag, photo mode, dialog, popover,
    menu, panel, selection, underground view, active tool. Only on an empty
    screen does Back show "Press Back again", and a second press within two
    seconds leaves the app;
  - Credits show the build: version, commit and platform.
- **Saves** stay where the web game keeps them (IndexedDB and localStorage),
  now inside the app's own WebView profile. That profile is tied to the app
  identifier.
  - **Windows:** `%LOCALAPPDATA%\<identifier>\EBWebView`.
  - **Android:** the app's private data.
  - **Updates:** installing a newer version with the same identifier (and, on
    Android, the same signing key) keeps saves.
  - **Uninstalling:** on Android this deletes saves; export them first. On
    Windows the uninstaller leaves the WebView profile in place.
  - **Import:** works through the game's import dialog, by picking a file or
    pasting the text.

## Security

- **Capabilities** (`src-tauri/capabilities/default.json`):
  - `core:default` and `core:app:allow-exit`, for the Android Back button;
  - `dialog:allow-save`;
  - `fs:allow-write-text-file` and `fs:allow-write-file`. These cover writing
    the file the player picked in the save dialog; the dialog adds that path
    to the allowed scope.
  - There is no shell, no process spawning, no HTTP, no read or list access to
    the file system, and no other window or webview API.
- **CSP** (`tauri.conf.json`):
  - scripts only from the app itself (`'self'`). Tauri adds the hashes of the
    two inline scripts at build time;
  - inline styles are allowed, because the game sets style attributes;
  - images and media from the app, `data:` and `blob:`;
  - network connections only to the app itself and Tauri's IPC;
  - no objects, no frames, no form posts.
- **No remote code.** Everything is packaged; the app does not need the
  internet to start.
- **Signing:** see [SIGNING.md](SIGNING.md).

## Versions and identifiers

| What | Where | Value |
|---|---|---|
| Release version | `node tools/version.mjs set X.Y.Z` | one version for package.json, game, Cargo, Tauri, service worker |
| Android versionCode | derived by `tools/version.mjs` | `(major·10000 + minor·100 + patch)·100 + (rc number, or 99 for a final release)` |
| App identifier | `src-tauri/tauri.conf.json` → `identifier` | `dev.tracklands.preview` (**development placeholder**, see SIGNING.md) |
| Tauri | `src-tauri/Cargo.toml`, `package.json` | tauri 2.12.1, CLI 2.12.1, dialog 2.8.1, fs 2.6.0 (pinned; `Cargo.lock` and `package-lock.json` committed) |
| Android | `src-tauri/gen/android` (generated by `tauri android init`, then customised) | minSdk 24 (Android 7.0), targetSdk / compileSdk 37, Gradle 9.6, AGP 9.3, NDK r29 (29.0.14206865) |
| Windows | NSIS, per-user install, WebView2 bootstrapper if missing | Windows 10 (1803+) and 11, x64 |

**Minimum Android 7.0 (API 24)** is Tauri's own minimum. TRACKLANDS needs no
newer platform API. It does need a current Android System WebView (ES
modules, import maps and WebGL), and the WebView updates through the Play
Store independently of the Android version.

### Changing the identifier

The identifier is also the Android package and the Kotlin source path, so
change it once, before the first public release:

1. Set `identifier` in `src-tauri/tauri.conf.json`.
2. Regenerate the Android project with the same customisations:
   1. Move `src-tauri/gen/android` aside.
   2. Run `npx tauri android init --ci`.
   3. Re-apply the signing block in `app/build.gradle.kts`.
   4. Re-apply `MainActivity.kt` (window insets).
   5. Re-apply the manifest change (no TV launcher entry).
   6. Re-apply `tracklands_bg` in `colors.xml` and both `themes.xml`.

   `git diff` against the old folder shows exactly what to re-apply.
3. Run the `native` workflow.

## Build locally

You need Node 22 and Rust (stable), plus the platform tools below.

```sh
npm ci
node tools/build-web.mjs --target=native     # also run automatically by tauri build
```

**Windows** (on Windows, with the MSVC build tools and WebView2):

```sh
npx tauri build --bundles nsis
# → src-tauri/target/release/bundle/nsis/TRACKLANDS_<version>_x64-setup.exe
```

**Android** (JDK 17 or newer, Android SDK, NDK r29; `ANDROID_HOME` and
`NDK_HOME` set; Rust targets `aarch64-linux-android`,
`armv7-linux-androideabi`, `i686-linux-android`, `x86_64-linux-android`):

```sh
# release signing (optional locally, needed for installable release builds):
node tools/ci/android-signing.mjs --keystore my.jks --alias me --store-password … --key-password …
npx tauri android build --apk --aab
node tools/ci/android-verify.mjs --out out --label local   # BUNDLETOOL_JAR for the AAB manifest check
```

Without `keystore.properties` the release APK is unsigned, and Android will
not install it. For a quick try on a device use `npx tauri android dev`.

**Linux** (development only; `libwebkit2gtk-4.1-dev` and friends):

```sh
npx tauri build --no-bundle && ./src-tauri/target/release/TRACKLANDS
```

## Tests

- `node tests/run.mjs nativebuild` covers:
  - the staging checks, music auto-inclusion and version drift;
  - native behaviour with the Tauri API present: no service worker, the save
    dialog and the Back order;
  - **the same simulation hash after 120 s of play** in the repository, the
    staged web build and the staged native build.
- `.github/workflows/native.yml` runs on every relevant push:
  - Rust format, check and clippy;
  - the Windows installer, with a silent install, launch until WebView2 has
    run the page, and silent uninstall;
  - the Android APK and AAB, signed with a throwaway key and verified for
    signature, id, version, ABIs and 16 KB page alignment;
  - an Android emulator run that boots the app, presses Back twice and
    restarts it.
